# Правила против дублирования знания

> Дублирование не сразу вредно. Оно вредно **потом** — когда одну копию обновили, а вторую забыли, и обе выглядят одинаково правдоподобно.
>
> Продукт уже объявил это принципом: «Каждая сущность имеет одно место хранения. Не допускается дублирование бизнес-смысла» ([`product/000`](../product/000-product-overview.md)). Этот документ распространяет принцип на документацию.

---

## 1. Purpose · Назначение

Сделать так, чтобы каждый факт о продукте существовал ровно в одном месте, а все остальные упоминания были ссылками — и чтобы нарушение можно было обнаружить проверкой, а не чутьём.

## 5. Validation Rules · Правила валидации

1. Ни одно понятие не встречается в поле `Defines` двух разных документов.
2. Каждое понятие из [`meta/007-ownership-map.md`](007-ownership-map.md) объявлено в `Defines` указанного там документа.
3. Ни один документ не содержит определения понятия, которым владеет другой документ.
4. Каждый обнаруженный дубликат либо устранён, либо имеет открытую запись в [`governance/decisions/000-decision-log.md`](../governance/decisions/000-decision-log.md).

## 6. Content · Содержание

### 6.1. Правило D1 — единственное определение

**Каждое понятие определяется ровно в одном документе.**

Этот документ называется **владельцем смысла**. Он объявляет понятие в поле `Defines`. Реестр владельцев — [`meta/007-ownership-map.md`](007-ownership-map.md).

Все прочие документы **ссылаются**:

> Прогресс рассчитывается по правилам [`domain/policies/progress-update-policy.md`](../domain/policies/progress-update-policy.md).

и **не пересказывают**:

> ~~Прогресс рассчитывается как среднее по навыкам с весами, где…~~

Пересказ — это копия, которая устареет.

### 6.2. Правило D2 — владелец определяется вопросом

Владельца смысла выбирают не по удобству, а по вопросу, на который отвечает знание.

| Вопрос о понятии | Владелец | Пример |
|------------------|----------|--------|
| Что это слово означает? | `language/001` | что такое «навык» |
| Как это устроено в модели? | `domain/` | из чего состоит `Skill`, какие события его меняют |
| Где пользователь это видит? | `experience/003` | экран «Навыки» |
| Как это работает для пользователя? | `features/catalog/` | фича «Карта навыков» |
| Как это выглядит? | `design/` | вид индикатора навыка |
| Когда мы это сделаем? | `roadmap/` | навыки в релизе 2 |

Одно понятие имеет **несколько аспектов**, у каждого аспекта **свой владелец**. Это не дублирование. Дублирование — когда два документа отвечают на **один и тот же** вопрос.

### 6.3. Правило D3 — что считается дубликатом

Дубликат:

- определение термина вне `language/001`;
- перечисление ролей вне `product/003`;
- перечисление границ продукта вне `product/002`;
- перечисление статусов фичи вне `features/002`;
- конкретное значение цвета, размера, длительности вне `design/011`;
- описание правила расчёта вне соответствующей политики `domain/policies/`;
- список экранов вне `experience/003`;
- пересказ бизнес-цели вне `product/006`.

Не дубликат:

- **ссылка** с указанием документа-владельца;
- **цитата** в 1–2 предложения с обязательной ссылкой на источник;
- **применение** правила к частному случаю («экран X подчиняется правилу PR-04»);
- **упоминание** id (`F-012`, `BG-03`, `SCR-114`) без раскрытия содержания.

### 6.4. Правило D4 — три разрешённые формы повторения

**Ссылка** — основная форма.

```markdown
Границы продукта: [`product/002-product-boundaries.md`](../product/002-product-boundaries.md).
```

**Цитата с атрибуцией** — когда без слов источника фраза непонятна. Максимум два предложения, всегда со ссылкой.

```markdown
> AI никогда не принимает окончательных педагогических решений самостоятельно.
> — [`product/000-product-overview.md`](../product/000-product-overview.md)
```

**Указатель (Pointer)** — целый документ, существующий только чтобы предотвратить создание дубликата. Пример: [`product/005-domain-glossary.md`](../product/005-domain-glossary.md) — глоссарий перенесён в `language/`, файл оставлен как указатель, чтобы никто не завёл второй глоссарий на привычном месте.

Указатель содержит только назначение и ссылку. Ни одного определения. Не более 15 строк.

### 6.5. Правило D5 — таблицы связей вместо копий

Часто хочется скопировать данные, чтобы «было под рукой». Вместо этого — **таблица связей**: только идентификаторы, без содержания.

Верно:

| Фича | Цель | Экран |
|------|------|-------|
| F-012 | BG-03 | SCR-114 |

Неверно:

| Фича | Описание фичи | Описание цели |
|------|---------------|---------------|
| F-012 | Карта навыков показывает… | Увеличить удержание… |

Второй вариант устареет в момент изменения любого из трёх документов.

### 6.6. Правило D6 — процедура при обнаружении дубликата

```
1. Определить, о каком ПОНЯТИИ идёт речь.
2. Найти владельца в meta/007-ownership-map.md.
   Владельца нет → определить по правилу D2 и внести в реестр.
3. Сравнить копии.
   Копии совпадают   → удалить лишнюю, поставить ссылку. КОНЕЦ.
   Копии расходятся  → это не дубликат, а ПРОТИВОРЕЧИЕ.
                       Перейти к meta/005-anti-contradiction-rules.md.
4. Проверить, что обе стороны связи Depends On / Required By обновлены.
```

Расходящиеся копии обрабатываются как противоречие, потому что удаление «лишней» копии здесь означало бы молчаливый выбор одной из двух версий истины.

### 6.7. Правило D7 — новый документ создаётся последним

Перед созданием файла:

1. Есть ли документ, отвечающий на этот же вопрос? → писать туда.
2. Есть ли документ, отвечающий на близкий вопрос? → расширить его раздел 6.
3. Знание не помещается никуда? → тогда новый документ, и он обязан объявить `Defines`, `Must Not Define` и быть внесён в [`meta/001-reading-order.md`](001-reading-order.md) и [`meta/007-ownership-map.md`](007-ownership-map.md) **в том же изменении**.

Документ без `Defines` не имеет права на существование: он ничем не владеет и, значит, дублирует что-то другое.

### 6.8. Известные точки риска дублирования

Места, где дубликат появляется чаще всего. Проверяются при каждой приёмке.

| Риск | Владелец смысла | Что не должно повторяться |
|------|-----------------|---------------------------|
| Термины | `language/001` | `domain/000`, `product/004`, `features/*` |
| Роли | `product/003` | `experience/*`, `features/*` |
| Границы продукта | `product/002` | `roadmap/004`, `product/000` |
| Правила расчёта | `domain/policies/*` | `features/catalog/*`, `experience/*` |
| Значения формы | `design/011` | `design/002`, `design/003`, `design/007` |
| Правила уведомлений | `domain/policies/notification-policy.md` | `experience/009` |
| AI-ограничения | `ai/006` | `features/catalog/*`, `product/000` |

### 6.9. Замечание о `domain/000-domain-overview.md`

Существующий документ [`domain/000-domain-overview.md`](../domain/000-domain-overview.md) содержит утверждение, что вся доменная терминология определяется в нём. С введением слоя `language/` владельцем определений терминов становится [`language/001-ubiquitous-language.md`](../language/001-ubiquitous-language.md).

Это **известное расхождение**, требующее решения. Порядок действий — по [`meta/005-anti-contradiction-rules.md`](005-anti-contradiction-rules.md): открыть PDR, зафиксировать разделение зон (`language/` — определения слов, `domain/` — структура модели), обновить оба документа. До принятия PDR оба документа считаются `Disputed` в части терминологии.
