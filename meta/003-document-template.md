# Шаблон документа

> Единая форма для всех документов репозитория. Форма не украшение: поля `Defines`, `Depends On` и `Required By` — это механизм, которым система защищается от дублирования и противоречий.

---

## 1. Purpose · Назначение

Задать обязательную форму документа так, чтобы её можно было проверить автоматически и чтобы каждый документ явно объявлял свою зону ответственности.

Позиция **0.4**. Обязателен для всех, кто пишет в репозиторий.

---

## 5. Validation Rules · Правила валидации

1. Каждый документ репозитория содержит все обязательные поля из раздела 6.1.
2. Каждый документ содержит разделы 1–6 из раздела 6.2 в указанном порядке.
3. Поле `Status` имеет значение из списка 6.3.
4. Ни один документ не содержит полей, отсутствующих в 6.1, без записи PDR.

## 6. Content · Содержание

### 6.1. Обязательный frontmatter

```yaml
---
Document Id: EXP-IA                    # уникальный идентификатор, UPPER-KEBAB
Title: Информационная архитектура       # человекочитаемое название
Layer: L5 · Experience — Опыт           # слой из meta/000, раздел 6.1
Status: Draft                          # значение из 6.3
Version: 0.3.0                         # semver, правила в meta/008
Last Updated: 2026-07-28               # ISO-8601, абсолютная дата
Reading Order: 5.2                     # позиция из meta/001
Authority Rank: 40                     # ранг слоя из meta/002
Authority Scope: Структура информации…  # одна фраза: над чем документ властен

Owners:                                # минимум один; роль, не имя
  - Product Owner
  - Design Lead

Depends On:                            # что прочитать ДО; пути от корня
  - product/004-core-concepts.md
  - language/001-ubiquitous-language.md

Required By:                           # что обновить ПОСЛЕ изменения
  - experience/002-navigation-model.md

Defines:                               # понятия, которыми документ ВЛАДЕЕТ
  - Иерархия разделов продукта
  - Правила группировки информации

Must Not Define:                       # чужие зоны; защита от расползания
  - Способ перехода между разделами (experience/002)
  - Визуальное оформление (design/)
---
```

**Назначение ключевых полей.**

| Поле | Механизм, который оно обслуживает |
|------|-----------------------------------|
| `Defines` | Правило единственного определения ([`meta/004`](004-anti-duplication-rules.md)). Понятие в `Defines` двух документов — ошибка. |
| `Must Not Define` | Предотвращает расползание документа в чужую зону. |
| `Depends On` | Задаёт порядок чтения и обязательный контекст перед изменением. |
| `Required By` | Задаёт каскад обновления ([`governance/001`](../governance/001-change-management.md)). |
| `Authority Rank` + `Authority Scope` | Разрешение конфликтов ([`meta/002`](002-authority-model.md)). |

**Правило симметрии.** Если A указывает B в `Depends On`, то B обязан указать A в `Required By`. Асимметрия — ошибка валидации.

### 6.2. Обязательные разделы

Порядок фиксирован. Разделы не переименовываются и не пропускаются.

```markdown
# {Title}

> Одно-два предложения: о чём документ и кому он нужен.

## 1. Purpose · Назначение
Зачем документ существует. Что сломается, если его не будет.

## 2. Owner · Владелец
Роли, отвечающие за содержание и актуальность.

## 3. Dependencies · Зависимости
Читать до / Зависит от — ссылками, дублирует frontmatter в читаемом виде.

## 4. Reading Order · Место в порядке чтения
Слой, позиция, ссылка на meta/001.

## 5. Validation Rules · Правила валидации
Нумерованный список проверяемых условий. Каждое — да/нет, без «должно быть хорошо».

## 6. Content · Содержание
Собственно знание. Единственный раздел, где оно допустимо.

## История изменений
Таблица: версия, дата, изменение.
```

**Разделы 1–5 — контракт.** Они действуют с момента создания файла, даже если раздел 6 пуст.

**Раздел 6 — единственное место знания.** Знание в разделах 1–5 — ошибка.

### 6.3. Значения `Status`

Множество состояний и правила переходов принадлежат [`meta/standard/001-document-lifecycle.md`](standard/001-document-lifecycle.md). Здесь приведено только их применение в форме документа.

| Status | Значение | Можно ли на него опираться |
|--------|----------|----------------------------|
| `Scaffold` | Создан скелет, содержания нет | Нет |
| `Draft` | Содержание пишется | Нет |
| `Review` | Содержание готово, идёт проверка | С осторожностью, отметив риск |
| `Approved` | Содержание проверено и принято владельцем | Да, в пределах зоны документа |
| `Canonical` | Зарегистрирован как единственный источник по своим понятиям | Да, безусловно |
| `Disputed` | Обнаружено противоречие, открыт PDR | Нет — до решения |
| `Superseded` | Заменён; содержит ссылку на замену | Нет |

Прежние значения `Accepted` и `Deprecated` выведены из употребления миграцией **M-0001** ([`meta/010-migration-register.md`](010-migration-register.md)). Соответствие: `Accepted → Approved`, `Deprecated → Superseded`.

**Правило опоры.** Документ со статусом `Approved` не может иметь в `Depends On` документ со статусом `Scaffold` или `Draft`. Документ со статусом `Canonical` не может зависеть от документа ниже `Approved`. Обратное допустимо.

### 6.3.1. Дополнительные поля при соответствии стандарту

| Поле | Когда обязательно |
|------|-------------------|
| `Standard Version` | для документов слоя `meta/`; для прочих — по завершении миграции M-0002 |
| Таблица вывода в конце раздела 6 | для каждого документа, содержащего нормативные утверждения ([`meta/standard/006-traceability.md`](standard/006-traceability.md), раздел 6.4) |

Отклонение DEV-0002 ([`meta/011-conformance-statement.md`](011-conformance-statement.md)) освобождает документы, созданные до 2026-07-28, от таблицы вывода до 2027-01-31.

### 6.4. Язык документов

- Язык содержания — **русский**, в соответствии со сложившейся практикой репозитория.
- Ключи frontmatter, идентификаторы, имена файлов — **английский**.
- Заголовки разделов 1–6 — двуязычные (`## 1. Purpose · Назначение`), чтобы форма читалась без перевода.

### 6.5. Что запрещено в любом документе

1. Определять понятие, объявленное в `Defines` другого документа.
2. Пересказывать содержание документа, на который можно сослаться.
3. Указывать конкретные значения, если их владелец — [`design/011-design-tokens.md`](../design/011-design-tokens.md).
4. Употреблять слова из [`language/004-forbidden-terms.md`](../language/004-forbidden-terms.md).
5. Оставлять относительную дату («на прошлой неделе», «скоро») — только абсолютные даты.
6. Помещать правило исключительно в изображение или диаграмму.
