# Правила против противоречий

> Противоречие — это два документа, дающих **разный ответ на один вопрос**, причём оба выглядят действующими.
>
> Полностью избежать противоречий нельзя. Можно сделать так, чтобы они **обнаруживались быстро** и **разрешались одинаково** независимо от того, кто их нашёл.

---

## 1. Purpose · Назначение

Свести к минимуму возможность противоречий структурно — и задать обязательную процедуру для тех, что всё-таки возникнут.

## 5. Validation Rules · Правила валидации

1. Ни один документ репозитория не находится в статусе `Disputed` дольше 14 дней без записи PDR.
2. Каждое обнаруженное противоречие имеет запись в [`governance/decisions/000-decision-log.md`](../governance/decisions/000-decision-log.md).
3. Ни один документ не переопределяет правило, объявленное в `Defines` документа с меньшим `Authority Rank`.
4. Каждое утверждение о будущем состоянии находится в слое L2–L8, а не в `school/`.

## 6. Content · Содержание

### 6.1. Виды противоречий

| Вид | Описание | Основная мера |
|-----|----------|---------------|
| **C1 · Прямое** | Два документа утверждают несовместимое об одном предмете | Правило единственного определения (D1) |
| **C2 · Скрытое** | Документы формально не спорят, но следствия несовместимы | Каскад `Required By` |
| **C3 · Временнóе** | Документ устарел после изменения другого | Версии и `Last Updated` |
| **C4 · Уровневое** | Нижний слой переопределяет решение верхнего | Правило направления зависимостей |
| **C5 · Терминологическое** | Одно слово в двух смыслах | Единый язык `language/001` |
| **C6 · Реальность / замысел** | `school/` описывает одно, `product/` требует другого | Разделение описательного и нормативного |

### 6.2. Структурные меры — противоречие не должно возникать

Все меры уже встроены в систему. Они работают, только если соблюдены.

**M1 · Единственный владелец смысла.** Если понятие определено один раз, противоречить нечему. Основная и самая дешёвая мера. См. [`meta/004`](004-anti-duplication-rules.md).

**M2 · Направление зависимостей.** Знание течёт `school → product → language → domain → experience → features → design → roadmap`. Документ не может переопределять то, что определено выше по течению. См. [`meta/000`](000-documentation-system.md), раздел 6.2.

**M3 · Обязательный каскад.** Поле `Required By` перечисляет документы, которые **обязаны** быть проверены при изменении. Изменение без проверки каскада — незавершённое изменение. См. [`governance/001`](../governance/001-change-management.md).

**M4 · Зоны авторитета.** Поля `Defines` и `Must Not Define` очерчивают границу. Документ, пишущий за границу, — источник будущего противоречия, даже если сегодня всё совпадает.

**M5 · Разделение описательного и нормативного.** `school/` описывает настоящее. Остальные слои описывают целевое. Разница между ними — не противоречие, а замысел. Утверждение о будущем в `school/` запрещено.

**M6 · Значения только в одном месте.** Конкретные числа, цвета, длительности живут в [`design/011-design-tokens.md`](../design/011-design-tokens.md). Число, скопированное в прозу, рано или поздно разойдётся с источником.

**M7 · Решения фиксируются.** Изменение смысла документа ранга ≤ 30 без PDR запрещено. PDR — единственный след, по которому видно, что противоречие было разрешено намеренно.

### 6.3. Процедура при обнаружении противоречия

Применяется одинаково человеком и AI-агентом.

```
ШАГ 1 · Зафиксировать
  Записать: документ A, документ B, предмет спора, оба утверждения дословно.

ШАГ 2 · Классифицировать
  Определить вид C1–C6 по таблице 6.1.

ШАГ 3 · Разрешить по meta/002
  Применить алгоритм meta/002-authority-model.md, раздел 6.3.
  Результат однозначен → ШАГ 4.
  Результат «остановиться» → ШАГ 5.

ШАГ 4 · Исправить
  Привести проигравший документ к победившему.
  Повысить его Version по meta/008.
  Проверить весь его Required By.
  Если изменён смысл документа ранга ≤ 30 → всё равно открыть PDR.
  КОНЕЦ.

ШАГ 5 · Эскалировать
  Пометить ОБА документа: Status: Disputed.
  В раздел 6 каждого добавить блок:
      > ⚠ DISPUTED: противоречие с {другой документ} по вопросу {предмет}.
      > Решение: PDR-XXXX. До принятия решения раздел не является истиной.
  Создать запись в governance/decisions/000-decision-log.md.
  ОСТАНОВИТЬСЯ. Не выбирать вариант самостоятельно.
```

**Запрет на молчаливое разрешение.** Выбрать «более правильный» вариант без записи — самая дорогая ошибка в системе: противоречие исчезает из виду, но причина расхождения остаётся неизвестной, и оно возвращается.

### 6.4. Статус `Disputed`

- Документ со статусом `Disputed` **не является истиной** в спорной части. Остальные его разделы продолжают действовать.
- Ни один новый документ не может ссылаться на спорный раздел.
- Статус снимается только записью PDR.
- Срок жизни статуса — не более 14 дней. Превышение — сигнал руководителю продукта.

### 6.5. Регулярная проверка

| Когда | Что проверяется | Кто |
|-------|-----------------|-----|
| При каждом изменении | Каскад `Required By` пройден | автор изменения |
| При приёмке | [`governance/002-review-checklist.md`](../governance/002-review-checklist.md) целиком | владелец документа |
| Ежемесячно | Симметрия `Depends On` / `Required By`; понятия без владельца; документы `Disputed` | Documentation Lead |
| При принятии PDR | Все документы из списка затронутых обновлены | Product Owner |

### 6.6. Открытые противоречия на момент создания системы

Фиксируются явно, чтобы не выглядели нормой.

Механика **обнаружения** расхождений (классы, детекторы, конкурирующие изменения) принадлежит [`meta/standard/009-conflict-detection.md`](standard/009-conflict-detection.md). Настоящий раздел ведёт перечень конкретных открытых расхождений этого репозитория.

| # | Предмет | Документы | Действие |
|---|---------|-----------|----------|
| 1 | Владелец определений терминов | `domain/000-domain-overview.md` ↔ `language/001-ubiquitous-language.md` | миграция **M-0003** ([`meta/010-migration-register.md`](010-migration-register.md)); PDR: `language/` — слова, `domain/` — структура модели |
| 2 | Владелец глоссария | `product/005-domain-glossary.md` ↔ `language/001-ubiquitous-language.md` | Разрешено: `product/005` переведён в тип Pointer |
| 3 | Продуктовые правила | `product/000-product-overview.md` (разделы «Принципы UX», «Архитектурные принципы») ↔ `product/009-product-rules.md` | PDR при наполнении `product/009`: правила переносятся, в `product/000` остаётся ссылка |

Пункты 1 и 3 обязаны быть закрыты до перевода зависимых документов в статус `Accepted`.
