## 5. Validation Rules · Правила валидации

1. Каждое состояние, используемое в репозитории, входит в множество DES-001, раздел 6.1.
2. Каждый порог раздела 6.1 выражен числом, а не описанием.
3. Ни один порог не превышает предела, заданного стандартом.
4. Каждый документ репозитория, использующий прежнее состояние, перечислен в миграции M-0001.

## 6. Content · Содержание

### 6.1. Пороги сроков

| Параметр | Значение | Требование стандарта |
|----------|----------|----------------------|
| Предельный срок в состоянии `Draft` | 90 дней | DES-001, 6.7 (L6) |
| Предельный срок в состоянии `Review` | 14 дней | DES-001, 6.7 (L6) |
| Предельный срок в состоянии `Disputed` | 14 дней | DES-001, 6.4 |
| Предельный срок в `Approved` без продвижения в `Canonical` | 60 дней | DES-001, 6.2 |
| Предельный срок бесхозного документа | 30 дней | DES-007, 6.8 |
| Переходный период после передачи владения | один цикл ревизии слоя | DES-007, 6.6 |
| Предельный срок открытого предложения | 14 дней | DES-009, 6.6 |
| Предельная доля просроченных канонических документов | 10 % | DES-001, 6.6 |

Превышение порога не меняет состояние автоматически. Оно порождает запись в отчёте Documentation Lead.

### 6.2. Интервалы ревизии

| Слой | Интервал | Что проверяется |
|------|----------|-----------------|
| `meta/`, `meta/standard/` | 6 месяцев | актуальность формы и процесса |
| `product/` | 6 месяцев | актуальность смысла |
| `school/` | 3 месяца | изменилась ли реальность |
| `language/`, `domain/` | при каждом изменении модели | синхронность |
| `experience/`, `features/`, `design/` | при каждом релизе | соответствие выпущенному |
| `roadmap/` | 1 месяц | соответствие фактическому ходу |
| `governance/`, `ai/` | 6 месяцев | применимость процесса |
| `assets/` | 12 месяцев | используемость материалов |

### 6.3. Соответствие прежних состояний

До введения стандарта репозиторий использовал иной набор состояний. Соответствие нормативно в течение окна миграции **M-0001** ([`meta/010-migration-register.md`](010-migration-register.md)).

| Прежнее состояние | Новое состояние | Примечание |
|-------------------|-----------------|------------|
| `Scaffold` | `Scaffold` | без изменений |
| `Draft` | `Draft` | без изменений |
| `Review` | `Review` | без изменений |
| `Accepted` | `Approved` | каноничность требует отдельной регистрации понятий |
| `Disputed` | `Disputed` | без изменений |
| `Deprecated` | `Superseded` | без изменений по смыслу |
| — | `Canonical` | новое состояние; присваивается только явной регистрацией |

**Правило окна.** В течение окна миграции обе формы допустимы при чтении. Новые и изменяемые документы ОБЯЗАНЫ использовать только новую форму.

**Важное следствие.** Документ, ранее помеченный `Accepted`, **не становится** `Canonical` автоматически. Он соответствует состоянию `Approved`. Перевод в `Canonical` требует регистрации его понятий в [`meta/007-ownership-map.md`](007-ownership-map.md) и каноничности всех его зависимостей (DES-001, переход T6).

### 6.4. Кто присваивает состояния

| Переход | Роль в этом репозитории |
|---------|-------------------------|
| `→ Scaffold`, `→ Draft` | автор |
| `→ Review` | владелец документа |
| `→ Approved` | владелец документа + независимый рецензент |
| `→ Canonical` | Documentation Lead как держатель реестра |
| `→ Disputed` | любой участник, включая AI-агента |
| `→ Superseded` | владелец + Documentation Lead |

Распорядитель по умолчанию для бесхозных документов — **Documentation Lead** (требование B3 стандарта).
