# Жизненный цикл документа

> Документ не бывает «просто написан». Он находится в одном из состояний, и от состояния зависит единственный практически важный вопрос: **можно ли на него ссылаться как на истину**.

---

## 1. Purpose · Назначение

Задать конечный автомат состояний документа так, чтобы в любой момент времени было машинно определимо, какие документы корпуса авторитетны, а какие — нет.

## 5. Validation Rules · Правила валидации

1. Каждый документ репозитория находится ровно в одном состоянии из раздела 6.1.
2. Каждый выполненный переход соответствует строке таблицы 6.3.
3. Ни один документ в состоянии `Canonical` не зависит от документа в состоянии ниже `Approved`.
4. Ни один документ не находится в состоянии `Draft`, `Review` или `Disputed` дольше порога, заданного привязкой.
5. Каждый документ в состоянии `Superseded` содержит ссылку на заменяющий документ.

## 6. Content · Содержание

### 6.1. Состояния

| Состояние | Смысл | Можно ссылаться как на истину | Кто переводит |
|-----------|-------|-------------------------------|---------------|
| `Scaffold` | Контракт документа (разделы 1–5) задан, содержание не написано | нет | автор |
| `Draft` | Содержание пишется | нет | владелец |
| `Review` | Содержание завершено, идёт независимая проверка | нет; ДОПУСКАЕТСЯ ссылаться с явной пометкой риска | владелец |
| `Approved` | Содержание проверено и принято владельцем | да, в пределах зоны документа | владелец + рецензент |
| `Canonical` | Документ зарегистрирован как единственный источник по своим понятиям | да, безусловно | держатель реестра |
| `Disputed` | Обнаружено расхождение; спорная часть недействительна | нет | любой обнаруживший |
| `Superseded` | Заменён другим документом; сохранён как история | нет | владелец + держатель реестра |

`Scaffold` — не черновик, а **объявленное намерение**: документ уже занимает место в структуре, объявил зону ответственности и критерии завершённости, но содержания не имеет. Это состояние существует, чтобы структура корпуса проектировалась раньше содержания.

### 6.2. Approved и Canonical — почему это разные состояния

Различие несёт основную нагрузку модели и не является формальностью.

| | `Approved` | `Canonical` |
|---|-----------|-------------|
| Что утверждено | **содержание** документа верно | документ является **единственным** источником по своим понятиям |
| Кто проверяет | владелец и рецензент | держатель реестра понятий |
| Что проверяется | правила раздела 5 документа, условия выхода DES-003 | регистрация понятий, отсутствие конкурирующих владельцев, каноничность зависимостей |
| Область проверки | документ | корпус |
| Можно ли цитировать как норму | да, в пределах зоны | да, безусловно |

Документ ОБЯЗАН быть верным (`Approved`) прежде, чем стать единственным источником (`Canonical`). Обратный порядок означал бы объявление источником истины непроверенного текста.

Документ может остановиться на `Approved` надолго и это нормально. Причины:

- его понятия ещё не зарегистрированы в реестре;
- одна из его зависимостей ещё не `Canonical`;
- существует конкурирующий документ, и вопрос владения не решён.

`Approved` без продвижения к `Canonical` дольше порога привязки — сигнал незакрытого вопроса владения, а не забывчивости.

### 6.3. Переходы

```
                    ┌──────────────────────────────────┐
                    │                                  │
Scaffold ──> Draft ──> Review ──> Approved ──> Canonical ──> Superseded
    │          ^         │            │             │              ^
    │          │         │            │             │              │
    │          └─────────┘            │             │              │
    │        (правки по замечаниям)   │             │              │
    │                                 v             v              │
    └────────────────────────────> Disputed <───────┘              │
                                      │                            │
                                      └────────────────────────────┘
                                       (разрешено записанным решением)
```

| # | Переход | Условие | Кто |
|---|---------|---------|-----|
| T1 | `— → Scaffold` | Выполнены условия входа DES-002 | автор |
| T2 | `Scaffold → Draft` | Начат раздел содержания | владелец |
| T3 | `Draft → Review` | Выполнены условия выхода DES-003 уровня «содержание завершено» | владелец |
| T4 | `Review → Draft` | Проверка выявила замечания | рецензент |
| T5 | `Review → Approved` | Чек-листы DES-004 и DES-005 пройдены; рецензент независим от автора | владелец + рецензент |
| T6 | `Approved → Canonical` | Понятия зарегистрированы; конкурирующих владельцев нет; все зависимости `Canonical` | держатель реестра |
| T7 | `Approved → Draft` | Требуется существенная переработка | владелец |
| T8 | `Canonical → Draft` | Требуется существенная переработка канонического документа | владелец + записанное решение |
| T9 | `* → Disputed` | Обнаружен конфликт (DES-009) | любой |
| T10 | `Disputed → предыдущее` | Конфликт разрешён записанным решением | держатель реестра |
| T11 | `Canonical → Superseded` | Принято решение о замене; заменяющий документ в состоянии `Canonical`; входящие ссылки перенаправлены | владелец + держатель реестра |
| T12 | `Approved → Superseded` | То же, для документа, не ставшего каноническим | владелец |

**Правила переходов.**

1. Пропуск состояний НЕ ДОПУСКАЕТСЯ. Переход `Scaffold → Approved` недействителен.
2. Переход T5 НЕ ДОПУСКАЕТСЯ, если рецензент совпадает с автором (см. DES-003).
3. Переход T6 НЕ ДОПУСКАЕТСЯ, если хотя бы одна зависимость документа не `Canonical`. Каноничность распространяется от корня графа зависимостей наружу.
4. Переход T8 ОБЯЗАН сопровождаться записанным решением: канонический документ является опорой других документов, и его переработка затрагивает корпус.
5. Переход T11 НЕ ДОПУСКАЕТСЯ до перенаправления всех входящих ссылок (DES-005).
6. Возврат из `Disputed` возможен только через записанное решение. Молчаливое снятие статуса НЕ ДОПУСКАЕТСЯ.
7. Документ НЕ ДОПУСКАЕТСЯ удалять. Вывод из обращения выполняется переходом в `Superseded`.

### 6.4. Состояние `Disputed`

`Disputed` — не стадия развития, а **прерывание**. Оно ортогонально прогрессу: документ входит в него из любого состояния и возвращается в то же.

Правила:

1. Документ в `Disputed` ОБЯЗАН содержать в начале раздела содержания блок с указанием: с каким документом расхождение, по какому вопросу, номер открытого решения.
2. Недействительной становится **только спорная часть**. Остальные разделы продолжают действовать.
3. Ни один новый документ НЕ ДОПУСКАЕТСЯ выводить из спорной части.
4. Продвижение по циклу заморожено: переходы T3, T5, T6 недоступны.
5. Превышение порога пребывания в `Disputed` — предмет эскалации, а не автоматического разрешения.

### 6.5. Связь версии и состояния

| Состояние | Версия | Правило |
|-----------|--------|---------|
| `Scaffold`, `Draft`, `Review` | `0.x.y` | документ не был принят ни разу |
| `Approved` (впервые) | `1.0.0` | первое принятие всегда даёт `1.0.0` |
| `Canonical` | `≥ 1.0.0` | регистрация не меняет версию |
| после `Canonical` | `MAJOR` | смысл изменился: прежние утверждения недействительны |
| | `MINOR` | добавлено знание, прежнее в силе |
| | `PATCH` | формулировка, ссылка, опечатка |

**Правила версии.**

1. Повышение `MAJOR` документа в состоянии `Canonical` ОБЯЗАНО сопровождаться записанным решением и повторным прохождением `Review`.
2. Повышение `MAJOR` ОБЯЗАНО запускать каскадную проверку всех зависимых документов (DES-005, DES-009).
3. Повышение `MINOR` ОБЯЗАНО запускать каскадную проверку; повторный `Review` НЕ ОБЯЗАТЕЛЕН.
4. Повышение `PATCH` не затрагивает состояние и каскад.
5. Любое повышение версии ОБЯЗАНО обновлять дату последнего изменения и добавлять строку в историю изменений.

### 6.6. Устаревание по времени

Документ не становится ложным сам по себе — ложной становится реальность вокруг него. Поэтому каноничность имеет **срок**.

1. Каждый класс документов ОБЯЗАН иметь интервал ревизии, задаваемый привязкой.
2. Документ, не проходивший ревизию дольше интервала, помечается как **просроченный**. Пометка не меняет состояние автоматически.
3. Просроченный документ СЛЕДУЕТ либо подтвердить (ревизия без изменений, `PATCH`, обновление даты), либо перевести в `Draft`.
4. Просроченный `Canonical` документ остаётся авторитетным: снятие авторитета без проверки создало бы пустоту вместо возможной неточности.
5. Доля просроченных канонических документов — метрика здоровья корпуса. Привязка ОБЯЗАНА задать её предельное значение.

### 6.7. Инварианты корпуса

Проверяются автоматически, независимо от отдельных документов.

| # | Инвариант |
|---|-----------|
| L1 | Каждый документ находится ровно в одном состоянии |
| L2 | Ни один `Canonical` документ не зависит от документа ниже `Approved` |
| L3 | Каждое зарегистрированное понятие принадлежит ровно одному `Canonical` документу |
| L4 | Каждый `Superseded` документ имеет ссылку на замену, и замена не `Superseded` |
| L5 | Ни один документ не ссылается на спорную часть `Disputed` документа |
| L6 | Ни один документ не пребывает в `Draft`, `Review`, `Disputed` дольше порога привязки |
| L7 | Граф зависимостей ацикличен |

Нарушение любого инварианта — дефект корпуса, а не отдельного документа, и адресуется держателю реестра.
