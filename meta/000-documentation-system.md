# Система документации Belcanto Product

> Этот документ описывает **как устроена документация**, а не сам продукт.
>
> Он отвечает на вопрос: «Почему документы лежат именно так и что можно писать в каждом из них?»
>
> Первый документ репозитория — [`docs/project/project-constitution.md`](../docs/project/project-constitution.md) на позиции `0.0`: он задаёт проектный контекст. Настоящий документ — **первый документ системы документации**, позиция `0.1`; любой человек или AI-агент читает его сразу после Конституции.

---

## 1. Purpose · Назначение

Задать структуру знания о продукте так, чтобы:

1. новый инженер понял продукт, прочитав **только документацию**;
2. каждый факт существовал **ровно в одном месте**;
3. при противоречии между документами существовал **однозначный ответ**, какой из них главный;
4. AI-агент мог работать с репозиторием **детерминированно**, а не по догадке.

---

## 2. Owner · Владелец

- Documentation Lead — форма, структура, целостность
- Product Owner — состав слоёв, право менять архитектуру документации

**Читать до этого документа:** графовых зависимостей нет — это точка входа системы документации.

[`docs/project/project-constitution.md`](../docs/project/project-constitution.md) читается **прежде** настоящего документа как контекст начальной загрузки проекта (позиция `0.0`). Это порядок чтения, а **не** ребро графа зависимостей: поле `Depends On` остаётся пустым, и Конституция не является предпосылкой настоящего документа (PD-0027; раздел 6.2.2 настоящего документа).

## 5. Validation Rules · Правила валидации

1. Каждый слой из раздела 6.1 существует в файловой системе.
2. Каждый документ, находящийся под контрактом документа, принадлежит ровно одному слою L0–L11. Единственное зарегистрированное исключение — область авторитета `Project` (раздел 6.2.2), содержащая контекст начальной загрузки проекта; она слоем не является и L12 не образует.
3. Каждый документ имеет разделы 1–5 из [`meta/003-document-template.md`](003-document-template.md).
4. Ни один документ не нарушает своё поле `Must Not Define`.

## 6. Content · Содержание

### 6.1. Слои документации

Документация разделена на слои. Слой отвечает на **один вопрос**. Документ не может отвечать на вопрос чужого слоя.

| # | Слой | Каталог | Вопрос слоя | Характер |
|---|------|---------|-------------|----------|
| L0 | Standard | `meta/standard/` | Как документы производятся? | нормативный (процесс), переиспользуемый |
| L0 | Meta | `meta/` | Как устроена документация? | нормативный (форма) |
| L1 | Reality | `school/` | Как школа работает **сегодня**? | описательный |
| L2 | Product | `product/` | Зачем существует продукт и каковы его границы? | нормативный (смысл) |
| L3 | Language | `language/` | Что означает каждое слово? | нормативный (термины) |
| L4 | Domain | `domain/` | Как устроена предметная область? | нормативный (модель) |
| L5 | Experience | `experience/` | Как продукт устроен для пользователя? | нормативный (структура) |
| L6 | Features | `features/` | Что продукт умеет делать? | нормативный (поведение) |
| L7 | Design | `design/` | Как продукт выглядит и звучит? | нормативный (форма) |
| L8 | Delivery | `roadmap/` | В каком порядке мы это делаем? | нормативный (план) |
| L9 | Governance | `governance/` | Кто и как принимает решения? | нормативный (процесс) |
| L10 | AI | `ai/` | Как AI-агент работает с репозиторием? | производный |
| L11 | Assets | `assets/` | Где лежат материалы? | ненормативный |

### 6.2. Направление зависимостей

Знание течёт **сверху вниз**:

```
school/  →  product/  →  language/  →  domain/  →  experience/  →  features/  →  design/  →  roadmap/
(факты)     (смысл)      (слова)       (модель)     (структура)     (поведение)   (форма)     (порядок)
```

**Правило направления.** Документ может ссылаться на любой документ **своего или предыдущего** слоя. Ссылка на последующий слой допускается только в поле `Required By` — как оповещение, а не как зависимость.

Нарушение правила направления — ошибка архитектуры документации, а не мелочь оформления. Оно означает, что решение принято не на своём уровне.

### 6.2.1. Стандарт и привязка

Слой `meta/` разделён на две части с разной природой:

| | `meta/standard/` — стандарт | `meta/` вне `standard/` — привязка |
|---|---|---|
| Содержит | требования к процессу производства документации | значения этих требований для данного репозитория |
| Зависит от предметной области | нет | да |
| Переносится в другой репозиторий | целиком | не переносится |
| Владелец | Standard Maintainer | Documentation Lead |
| Ранг | 3 | 5 |

Стандарт без привязки неработоспособен: он оперирует абстракциями («вышестоящий документ», «порог», «владеющая роль»), значения которым даёт привязка. Требования к привязке — [`meta/standard/016-conformance-and-binding.md`](standard/016-conformance-and-binding.md); текущее покрытие — [`meta/011-conformance-statement.md`](011-conformance-statement.md).

### 6.2.2. Корень проекта и граф вывода

[`docs/project/project-constitution.md`](../docs/project/project-constitution.md) — **контекст начальной загрузки проекта**. Он находится **вне** двенадцати слоёв L0–L11 и дополнительным слоем документации не является.

| Свойство | Значение |
|----------|----------|
| Позиция чтения | `0.0` — зарегистрирована в [`meta/001`](001-reading-order.md) |
| Когда читается | прежде настоящего документа |
| Значение поля `Layer` | `Project` — зарегистрированная **область авторитета** вне L0–L11; не слой документации и не L12 |
| Чем управляет | рабочий процесс проекта, инженерная философия, проектные выборы — в пределах своей `Authority Scope` |
| Чем не управляет | продуктовая истина: она остаётся за продуктовыми документами |

**Корень не входит в граф вывода.** Продуктовые документы, на которые Конституция ссылается в содержании и таблице вывода, являются **атрибутированными авторитетами**: ссылка указывает происхождение утверждения и **не образует ребра графа**. Поэтому правило раздела 6.2 — документ не читается раньше своих зависимостей — к таким ссылкам не применяется: зависимостей у корня нет.

Регистрация в реестре порядка чтения фиксирует позицию и **не делает реестр зависимым** от корня.

Внутри графа вывода правило направления зависимостей действует без изменений.

**Рабочие ярлыки.** Выражения «корень начальной загрузки проекта» и «контекст начальной загрузки проекта» — рабочие обозначения одного и того же нормативного контекста `Project`. Они не вводят ни типа документа, ни слоя документации, ни отдельно владеемого понятия.

**Регистрация авторитета.** Область `Project` зарегистрирована с рангом **4** в [`meta/002`](002-authority-model.md), раздел 6.1. Настоящий раздел лишь указывает на владельца иерархии авторитета и её не переопределяет.

Основание: **PD-0027** (положение корня и рабочие ярлыки), **PD-0028** (регистрация области авторитета).

### 6.3. Три служебных слоя

- `governance/` — стоит **сбоку** от цепочки. Принятое решение (PDR) изменяет документ любого слоя.
- `ai/` — **производный**. Не содержит собственной истины, только правила обращения с чужой.
- `assets/` — **ненормативный**. Материал никогда не является источником истины. Если правило существует только на картинке — его не существует.

### 6.4. Типы документов

| Тип | Признак | Пример |
|-----|---------|--------|
| **Overview** | `000-*` в каталоге; объясняет состав слоя | `experience/000-experience-overview.md` |
| **Definition** | определяет понятия; является владельцем смысла | `language/001-ubiquitous-language.md` |
| **Catalog** | реестр однотипных объектов с id | `features/000-feature-catalog.md` |
| **Rules** | набор проверяемых утверждений | `product/009-product-rules.md` |
| **Record** | неизменяемая запись факта или решения | `governance/decisions/records/PDR-0001-*.md` |
| **Template** | обязательная форма для других документов | `features/001-feature-template.md` |
| **Pointer** | указатель на владельца смысла; не содержит знания | `product/005-domain-glossary.md` |

### 6.5. Два несущих правила

**Правило 1 — одна ответственность.**
Документ отвечает на один вопрос. Если документ отвечает на два — его делят.

**Правило 2 — единственное определение.**
Каждое понятие определяется **ровно в одном** документе. Этот документ объявляет понятие в поле `Defines`. Все остальные документы **ссылаются**, но не пересказывают.

Разворачивание обоих правил: [`meta/004-anti-duplication-rules.md`](004-anti-duplication-rules.md).

### 6.6. Что делать, если знание не помещается ни в один слой

Не создавать новый файл «на всякий случай». Порядок действий:

1. Определить, на какой **вопрос** отвечает знание.
2. Найти слой с таким вопросом (раздел 6.1).
3. Если слоя нет — открыть решение в `governance/decisions/`. Новый слой создаётся только через PDR.
