# Общие правила валидации

> Правила из раздела 5 каждого документа — частные. Здесь собраны те, что действуют **везде и всегда**.
>
> Правило, которое нельзя проверить ответом «да / нет», правилом не является.
>
> **Отношение к стандарту.** Обязательный состав проверок и требование их автоматизации принадлежат [`meta/standard/004-validation-checklist.md`](standard/004-validation-checklist.md). Настоящий документ — его реализация в этом репозитории: конкретные имена полей, пороги и действия при нарушении. Проверки ссылок, вынесенные стандартом в отдельный документ, здесь не дублируются — см. [`meta/standard/005-cross-reference-checklist.md`](standard/005-cross-reference-checklist.md).

## 1. Purpose · Назначение

Дать единый набор проверок, применимых к любому документу репозитория, чтобы качество документации не зависело от внимательности конкретного автора.

## 5. Validation Rules · Правила валидации

1. Каждое правило раздела 6 проверяемо ответом «да / нет».
2. Ни одно правило раздела 6 не дублирует правило из раздела 5 другого документа.
3. Каждое правило указывает, что делать при нарушении.

## 6. Content · Содержание

### 6.1. Уровень 1 — форма (проверяется автоматически)

| # | Правило | При нарушении |
|---|---------|---------------|
| V1.1 | Присутствуют все обязательные поля frontmatter | документ не принимается |
| V1.2 | `Status` имеет значение из [`meta/003`](003-document-template.md), раздел 6.3 | документ не принимается |
| V1.3 | `Version` соответствует semver | документ не принимается |
| V1.4 | `Last Updated` — абсолютная дата ISO-8601 | документ не принимается |
| V1.5 | Присутствуют разделы 1–6 в указанном порядке | документ не принимается |
| V1.6 | Все внутренние ссылки ведут на существующие файлы | документ не принимается |
| V1.7 | Позиция `Reading Order` совпадает с [`meta/001`](001-reading-order.md) | обновить `meta/001` |
| V1.8 | `Authority Rank` равен рангу слоя по [`meta/002`](002-authority-model.md) | исправить документ |

### 6.2. Уровень 2 — связи (проверяется автоматически)

| # | Правило | При нарушении |
|---|---------|---------------|
| V2.1 | Симметрия: A в `Depends On` B ⟺ B в `Required By` A | добавить недостающую сторону |
| V2.2 | Все `Depends On` стоят раньше в [`meta/001`](001-reading-order.md) | нарушено направление зависимостей — переносить знание, а не ссылку |
| V2.3 | Документ `Accepted` не зависит от `Scaffold` или `Draft` | понизить `Status` или дописать зависимость |
| V2.4 | Каждое понятие в `Defines` уникально по репозиторию | применить [`meta/004`](004-anti-duplication-rules.md), раздел 6.6 |
| V2.5 | Каждое понятие в `Defines` внесено в [`meta/007`](007-ownership-map.md) | обновить реестр |
| V2.6 | В графе `Depends On` нет циклов | разорвать цикл, вынеся общее знание выше |

### 6.3. Уровень 3 — содержание (проверяется человеком)

| # | Правило | При нарушении |
|---|---------|---------------|
| V3.1 | Знание находится только в разделе 6 | перенести |
| V3.2 | Документ не определяет ничего из `Must Not Define` | перенести к владельцу, оставить ссылку |
| V3.3 | Документ не пересказывает то, на что можно сослаться | заменить ссылкой |
| V3.4 | Каждый термин употреблён в значении [`language/001`](../language/001-ubiquitous-language.md) | исправить или дополнить каталог |
| V3.5 | Нет слов из [`language/004`](../language/004-forbidden-terms.md) | заменить |
| V3.6 | Правила раздела 5 проверяемы «да / нет» | переформулировать |
| V3.7 | Ни одно правило не существует только на картинке | вынести в текст |
| V3.8 | Нет относительных дат | заменить абсолютными |
| V3.9 | Неподтверждённое утверждение помечено как гипотеза | пометить или удалить |
| V3.10 | Документ не противоречит документу меньшего ранга по своей зоне | [`meta/005`](005-anti-contradiction-rules.md), раздел 6.3 |

### 6.4. Уровень 4 — целостность репозитория (ежемесячно)

| # | Правило | При нарушении |
|---|---------|---------------|
| V4.1 | Каждый файл присутствует в [`meta/001`](001-reading-order.md) | внести |
| V4.2 | Каждый документ имеет непустое `Defines` | документ ничем не владеет — объединить с другим |
| V4.3 | Нет документов `Disputed` старше 14 дней | эскалация Product Owner |
| V4.4 | Нет документов `Draft` старше 90 дней | перевести в `Accepted` или `Deprecated` |
| V4.5 | Каждый файл `assets/` упомянут хотя бы в одном документе | удалить неиспользуемый |
| V4.6 | Каждый принятый PDR применён ко всем затронутым документам | завершить применение |
| V4.7 | Каждый id (`F-XXX`, `SCR-XXX`, `BG-XX`, `PR-XX`, `PDR-XXXX`) уникален | переназначить |

### 6.5. Порядок проверки

Уровни проверяются по возрастанию. Провал уровня останавливает проверку: нет смысла проверять содержание документа, в котором сломаны ссылки.

```
Уровень 1 (форма) → Уровень 2 (связи) → Уровень 3 (содержание) → Уровень 4 (репозиторий)
```

### 6.6. Когда что проверяется

| Событие | Уровни |
|---------|--------|
| Создание документа | 1, 2 |
| Изменение документа | 1, 2, 3 |
| Перевод в `Accepted` | 1, 2, 3 |
| Принятие PDR | 1, 2, 3 + V4.6 |
| Ежемесячная ревизия | 4 |

### 6.7. Правило неполной проверки

Документ, прошедший не все применимые уровни, **не может получить статус `Accepted`**. Промежуточный результат фиксируется статусом `Review`, а не молчаливым принятием.
