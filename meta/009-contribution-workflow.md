# Порядок внесения изменений

> Как физически внести изменение в репозиторий так, чтобы система осталась целостной.
>
> **Отношение к стандарту.** Условия создания и завершённости документа принадлежат [`meta/standard/002-entry-criteria.md`](standard/002-entry-criteria.md) и [`meta/standard/003-exit-criteria.md`](standard/003-exit-criteria.md); протокол изменений AI-агентом — [`meta/standard/008-agent-change-protocol.md`](standard/008-agent-change-protocol.md). Здесь описана механика: последовательность действий, атомарность и форма сообщения об изменении.

---

## 1. Purpose · Назначение

Задать одинаковый порядок работы для человека и AI-агента, при котором незавершённое изменение видно сразу, а не через месяц.

## 6. Content · Содержание

### 6.1. Порядок работы

```
1. ОПРЕДЕЛИТЬ ПОНЯТИЕ
   Какое понятие затрагивается? → meta/007-ownership-map.md
   Владельца нет → meta/004, правило D7.

2. ПРОЧИТАТЬ
   Документ-владелец + всё из его Depends On.
   Раньше не читал meta/002 → прочитать сейчас.

3. ПРОВЕРИТЬ НА ДУБЛИРОВАНИЕ
   Знание уже где-то есть? → писать туда, здесь поставить ссылку.

4. ИЗМЕНИТЬ ОДИН ДОКУМЕНТ
   Правка только в разделе 6.
   Затронуты Defines / Must Not Define → обновить frontmatter.

5. ПОВЫСИТЬ ВЕРСИЮ
   По meta/008, раздел 6.3. Обновить Last Updated и «Историю изменений».

6. ПРОЙТИ КАСКАД
   Открыть каждый документ из Required By.
   Не затронут → отметить. Затронут → править. Противоречит → meta/005.

7. ОБНОВИТЬ РЕЕСТРЫ
   Новый документ  → meta/001-reading-order.md
   Новое понятие   → meta/007-ownership-map.md
   Новый id        → соответствующий каталог

8. ПРОВЕРИТЬ
   meta/006-validation-rules.md, уровни 1–3.
   Приёмка → governance/002-review-checklist.md.

9. ЗАФИКСИРОВАТЬ РЕШЕНИЕ
   Изменён смысл документа ранга ≤ 30 → записанное решение обязательно.
   Канонический реестр недоступен → запись PD-XXXX в
   governance/decisions/002-pending-decisions.md, перенос позднее.
   Остановка производства продукта из-за недоступности реестра
   НЕ ДОПУСКАЕТСЯ (PD-0004).
```

### 6.2. Атомарность изменения

Одно изменение — один смысловой шаг. Внутри одного изменения обязаны находиться:

- изменённый документ;
- все документы каскада, потребовавшие правки;
- обновлённые реестры (`meta/001`, `meta/007`);
- запись PDR, если она требуется.

Разделение этих частей на несколько изменений оставляет репозиторий в противоречивом состоянии между ними.

### 6.3. Сообщение об изменении

```
docs(<слой>): <что изменилось>

Понятие: <затронутое понятие>
Владелец: <документ-владелец>
Каскад: <документы из Required By: проверены / изменены>
PDR: <PDR-XXXX или «не требуется»>
```

Пример:

```
docs(experience): добавлено правило подтверждения необратимых действий

Понятие: Сквозные правила взаимодействия
Владелец: experience/010-interaction-rules.md
Каскад: design/007 (проверен, не затронут), features/001 (обновлён шаблон)
PDR: не требуется (ранг 40, MINOR)
```

### 6.4. Определение завершённого изменения

Изменение завершено, когда выполнены **все** условия:

1. Документ изменён и его правила раздела 5 выполнены.
2. Версия повышена, `Last Updated` обновлён, «История изменений» дополнена.
3. Каждый документ из `Required By` открыт и его состояние определено.
4. Симметрия `Depends On` / `Required By` сохранена.
5. Реестры обновлены.
6. Уровни валидации 1–3 пройдены.
7. PDR создан, если требуется.

Невыполнение любого пункта означает, что изменение не завершено. Незавершённое изменение не сливается в основную ветку.

### 6.5. Кто что может менять

| Кто | Может менять | Не может |
|-----|--------------|----------|
| Владелец документа | свой документ до `MINOR` | чужие документы |
| Владелец документа | свой документ до `MAJOR` при наличии PDR | — |
| Любой участник | предложить изменение, открыть PDR, пометить `Disputed` | принимать `Accepted` |
| Product Owner | любой документ через PDR | обходить PDR для ранга ≤ 30 |
| AI-агент | по [`ai/004-task-playbooks.md`](../ai/004-task-playbooks.md), в пределах [`ai/005-prohibited-actions.md`](../ai/005-prohibited-actions.md) | принимать решения, разрешать противоречия |

### 6.6. Частая ошибка

Самая распространённая ошибка — **шаг 6 пропущен**. Документ изменён, каскад не пройден, противоречие возникает не сразу, а при следующем чтении зависимого документа — когда причина уже забыта.

Поле `Required By` существует именно для этого шага и заполняется даже тогда, когда кажется пустым.
