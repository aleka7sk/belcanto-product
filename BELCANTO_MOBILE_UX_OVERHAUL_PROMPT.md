## §1. Роль и планка качества

Ты — **CTO и Head of Design** продукта Belcanto (мобильное приложение вокальной
школы). Владелец продукта посмотрел приложение на устройстве и увидел то, что
недопустимо для продукта его уровня: таб-бар «плывёт» по экрану вместо того,
чтобы быть прибитым к низу; кнопки разных размеров; перегруженные простыни
вместо экранов; трудно понять, что к чему. Твоя задача — довести исполнение до
планки **мобильных LinkedIn и YouTube**.

«Уровень LinkedIn/YouTube» — это не вкусовщина, а проверяемые критерии. Считай
их definition of done всей работы:

1. **Навигация всегда прибита.** Нижний таб-бар зафиксирован у нижней кромки на
   каждом экране, где он должен быть, с учётом safe-area. Он никогда не
   скроллится с контентом и никогда не исчезает там, где пользователь ждёт его.
2. **Один scaffold на всё приложение.** Каждый экран собран из одного и того же
   каркаса: safe-area, скролл, слот навигации, слот sticky-заголовка,
   pull-to-refresh. Ноль ручных ScrollView-обвязок.
3. **Каждая интерактивная цель ≥ 48pt.** Без исключений: чипы, чекбоксы,
   текстовые действия — либо ≥48pt визуально, либо 48pt hit-area через
   hitSlop/padding. `minHeight`, не `height` — интерфейс растёт с системным
   масштабом шрифта.
4. **Одна система токенов.** Один источник цвета/типографики/отступов/радиусов.
   Никаких «legacy» и «modern» слоёв одновременно.
5. **Один экран — одна задача.** Progressive disclosure: длинные простыни
   разбиваются на экраны/шиты по раскадровке Figma. Пользователь всегда
   понимает, где он и что от него хотят.
6. **Списки виртуализированы.** Ленты и каталоги — FlatList, не
   ScrollView+map.
7. **Предсказуемые паттерны.** Один SegmentedControl, один Button API, один
   стиль заголовка экрана. Увидел паттерн один раз — узнаёшь его везде.

Роль CTO означает: ты не просто чинишь баги — ты фиксируешь целевую
архитектуру, объявляешь устаревшее устаревшим и доводишь миграцию до конца,
а не до «работает и ладно».

## §3. Вшитые seed-факты аудита

Ниже — результат разведки кода предыдущей сессией. Статус каждого факта:
**«проверь, подтверди, расширь»**. Номера строк могли уехать — сверяй по
содержимому, не слепо.

### 3.1. Две несовместимые архитектуры экрана (корень «плывущего» таб-бара)
- `AccountScreenShell` (`apps/mobile/src/ui/patterns/accountPatterns.tsx:43`) —
  правильный каркас: ScrollView + навигация **вне** скролла, absolute у нижней
  кромки, safe-area через `useSafeAreaInsets`. Используется ~38 экранами.
- `PremiumScrollScreen` (`apps/mobile/src/ui/components.tsx:48`) — **не имеет
  слота навигации вовсе** и ставит `minHeight: height` (полный вьюпорт) на
  контент. Используется ~14 экранами.
- **Три экрана кладут `RoleBottomNav` внутрь скролла последним ребёнком** —
  таб-бар скроллится с контентом, и до него нужно пролистать целый экран:
  - `src/ui/screens/ScheduleScreen.tsx` (~строка 266),
  - `src/ui/screens/LessonDetailScreen.tsx` (~139),
  - `src/ui/screens/StudentHomeScreen.tsx` (~200; этот экран ещё и
    ре-имплементирует скролл-обвязку руками вместо общего компонента).
  Это первые экраны, которые видит ученик — именно их владелец описал как
  «navigation tab плывёт по всему экрану».
- `RoleBottomNav` (`src/ui/roleNavigation.tsx:33`) сам по себе — плавающая
  пилюля без позиционирования и без safe-area; размещение на совести
  вызывающего. Высота 68 захардкожена **дважды**: `roleNavigation.tsx` (~80) и
  `accountPatterns.tsx` (~46) — без общего токена.
- `SafeAreaView` не используется нигде; только ручная математика инсетов в
  5 местах.

### 3.2. Мёртвые концы навигации
- **~14 protected-экранов вообще без нижней навигации**, часть достижима прямо
  из табов: таб Owner `team` → `AccessDelegationScreen` (без нава — тупик);
  таб Admin `people` → `StaffWorkspaceScreen` (без нава).
- Таб `schedule` есть у **всех четырёх ролей**
  (`src/navigation/tabs.ts:47-70`), но `ScheduleScreen` жёстко гардит
  `roles.includes("Student")` → педагог/админ/владелец попадают на «Раздел
  недоступен» внутри `PremiumScrollScreen` **без навигации, чтобы уйти**.

### 3.3. Разнобой интерактивных целей (≥6 разных размеров)
- `PrimaryButton` — фиксированный `height: 48` (не растёт с масштабом шрифта);
  `SecondaryButton`/`TextAction` — `minHeight: 48`; `BlockAction`
  (accountPatterns) — `minHeight: 52`; `DateChip` — 64.
- **Ниже минимума 48pt**: `AreaChip` и `FilterChip` — `height: 34`; `TaskRow`
  (чекбокс задачи) — `minHeight: 32`; действие «Пожаловаться» под комментарием
  (`communityPatterns.tsx`, ~312) — `minHeight: 24`; ad-hoc сегменты — 38.
- Токен `sizes.touchMin = 48` (`tokens.ts:192`) используется **ровно один
  раз** во всём приложении; `MINIMUM_INTERACTIVE_TARGET = 48`
  (`src/accessibility/policy.ts:1`) задекларирован, но к компонентам не
  применён.

### 3.4. Две параллельные системы токенов
- `tokens.ts` (~строка 290) сам признаёт: legacy-экспорт
  (`colors/fonts/typeScale/spacing/metrics/radii`) существует «до миграции»;
  modern-слой — `semantic/typeStyles/space/radius/sizes`.
- Legacy-only: **14 экранов** (`AccessDelegation`, `CreateLesson`,
  `CreateStudent`, `LessonDetail`, `OnboardingDetail`, `Schedule`,
  `SessionRecovery`, `SignIn`, `StaffLessons`, `StaffWorkspace`,
  `StudentHome`, `TeacherChange`, `Welcome`, частично `Activation`) **плюс два
  shared-модуля** — `components.tsx` и `lessonComponents.tsx`. Из-за shared
  legacy протекает во **все** современные экраны через `PremiumTextField` и
  `InlineNotice`.
- `ActivationScreen.tsx` (793 строки) использует обе системы в одном файле.
- Шкалы не конгруэнтны: `spacing.field = 18`, `spacing.section = 30` не имеют
  эквивалента в `space`.

### 3.5. Перегруз экранов (источник «трудно разобраться»)
- `/progress` (`StudentProgressScreen` + `GrowthSections.tsx`, 584 строки):
  **~24 кнопки и ~10 текстовых полей в одном непрерывном скролле**.
- `community/PostDetailScreen.tsx`: **три отдельных Figma-экрана слиты в один
  скролл** — тред (COM-POST-01) + жалоба (COM-SAFE-02) + блокировка
  (COM-SAFE-03); три `ScreenHeading` и 7 `BlockAction` на одной странице.
- `practice/HomeworkDetailScreen.tsx` (501 строка): ~15 действий и 6 полей в
  одной колонке.
- **Ключевой инсайт**: в Figma это ОТДЕЛЬНЫЕ экраны. Перегруз — следствие
  слияния раскадровки в простыни. Лечение — вернуться к раскадровке Figma:
  отдельные роуты и bottom-sheets, а не аккордеон в одном скролле.

### 3.6. Дублирование паттернов
- **Три почти byte-identical копии сегмент-контрола** (`minHeight: 38`):
  `OwnerOverviewScreen.tsx`, `teacher/TeacherStudentsScreen.tsx`,
  `community/CommunityScreen.tsx` — ручные `.map()+Pressable` без
  `accessibilityRole="tablist"`.
- Плюс разрозненные фильтр-ряды: `AreaChip`-ряд в прогрессе, `FilterChip`-ряд в
  каталоге событий — та же идея, разные компоненты.

### 3.7. Списки и производительность
- **Ноль виртуализации**: ни одного `FlatList`/`SectionList` в приложении;
  95 вызовов `.map()` в ScrollView. Ленты (активность, сообщество, каталог
  событий, модерация, репертуар) монтируют все строки сразу.
- `AccountScreenShell` **не пробрасывает** `scrollProps`/`refreshControl` →
  pull-to-refresh невозможен на 38 экранах. Он есть только на двух
  staff-экранах через escape-hatch `PremiumScrollScreen`.

## §4. Фаза A — Доскональный аудит

Прежде чем менять код — проведи полный аудит и зафиксируй findings. Seed-факты
из §3 — отправная точка: подтверди их по текущему коду и **расширь** по осям:

1. **Навигационная архитектура**: где нав прибит / скроллится / отсутствует;
   тупики; соответствие табов ролям (`src/navigation/tabs.ts`) и маршрутам
   (`src/ui/screens/account/shared.tsx`).
2. **Scaffold-инвентарь**: каждый экран → какой каркас использует.
3. **Тач-цели**: каждый интерактивный элемент → фактическая высота/hit-area;
   поведение при системном масштабе шрифта (Dynamic Type).
4. **Токены**: полная карта legacy/modern по файлам.
5. **Плотность и IA**: для каждого тяжёлого экрана — сколько
   заголовков/карточек/действий в одном скролле и какой раскадровке Figma это
   противоречит (сверяйся с живой Figma через MCC: `get_metadata` страницы →
   `get_design_context` фрейма; Figma read-only).
6. **Списки/перфоманс**: все `.map()`-ленты, кандидаты на FlatList,
   отсутствие pull-to-refresh.
7. **Доступность**: roles/labels/state на интерактивных элементах, tablist у
   сегментов, целевые размеры, контраст по токенам.
8. **Консистентность**: заголовки экранов (eyebrow/title/subtitle) и копий,
   единообразие пустых состояний, ошибок и retry.

**Формат каждого finding**: `файл:строка · P0/P1/P2 · что не так · как
воспроизвести на устройстве · какому экрану/инварианту Figma противоречит`.
P0 — ломает базовый UX (плывущий нав, тупики, цели <40pt); P1 — системная
непоследовательность (токены, дубли, перегруз); P2 — полировка.

Сохрани отчёт аудита в
`.claude/implementation/ux-overhaul-audit.md` (рабочий артефакт реализации, не
корпус).

## §5. Фаза B — Стратегия (реши до первой правки)

Зафиксируй целевую архитектуру письменно (в том же audit-файле, раздел
«Target»), затем исполняй. Направление задано владельцем, менять его нельзя —
можно уточнять детали:

1. **Единый `Screen` scaffold** — эволюция `AccountScreenShell`:
   - навигация всегда прибита, высота — из общего токена (устранить дубли 68);
   - safe-area сверху/снизу; `minHeight: height` убрать;
   - слоты: `refreshControl`, `scrollProps`, sticky-заголовок, режим формы
     (KeyboardAvoiding);
   - `PremiumScrollScreen` и все ручные ScrollView-обвязки — deprecated,
     мигрировать и удалить.
2. **Один Button API**: primary/secondary/text/pill; все ≥48pt через
   `sizes.touchMin`; `minHeight`, не `height`; чипы — визуально 34, hit-area 48
   (hitSlop). `BlockAction` и `Primary/SecondaryButton` сходятся в один
   компонент (или один делегирует другому) — не три реализации.
3. **Один `SegmentedControl`** с `accessibilityRole="tablist"` — заменить три
   копии и разрозненные фильтр-ряды, где это семантически табы.
4. **Токены — одна система**: мигрировать `components.tsx` и
   `lessonComponents.tsx` на semantic/typeStyles/space (это разблокирует всё),
   затем 14 legacy-экранов, затем удалить legacy-слой из `tokens.ts` (значения
   не выдумывать — соответствия брать из Figma-токенов; отсутствующие в
   modern-шкале значения 18/30 согласовать с `design/011-design-tokens.md`,
   а не добавлять в обход корпуса).
5. **IA-декомпозиция по Figma-раскадровке**:
   - `PostDetailScreen` → тред; жалоба — отдельный роут
     (`/community/report?...`); блокировка — bottom-sheet/отдельный экран;
   - `/progress` → обзорный экран + отдельные разделы (цели, достижения,
     ревью) вместо трёх форм в одном скролле;
   - `HomeworkDetailScreen` → статус/просмотр отдельно от пошаговых действий.
6. **FlatList** для лент: активность, лента сообщества, каталог событий,
   очередь модерации, репертуар, ростер учеников.

Что **не** входит в скоуп: серверный API, контракты, корпус документации,
новые продуктовые возможности. Любое расхождение кода с Approved-документом
корпуса решается в пользу документа.

## §6. Фаза C — Исполнение (порядок владельца: фундамент → ученик)

Не останавливайся после аудита и стратегии — исполняй срезы подряд, каждый до
зелёных гейтов и чекпоинта.

**Срез 1 — Фундамент (P0):**
- Единый `Screen` scaffold; общий токен высоты нава; safe-area.
- Перевести 3 «плывущих» экрана (Schedule, LessonDetail, StudentHome) и все
  без-нав экраны на единый scaffold; починить тупики (нав на
  AccessDelegation/StaffWorkspace; таб `schedule` для staff ведёт на их
  расписание `StaffLessonsScreen`, а не на гард).
- Единый Button API + 48pt-минимум везде; единый SegmentedControl.
- Миграция shared-модулей (`components.tsx`, `lessonComponents.tsx`) на
  semantic-токены.
- Гейты → коммит → ledger → push.

**Срез 2 — Контур ученика, экран за экраном:**
Вход → Дом → Расписание → Урок → Практика/Домашние → Прогресс (декомпозиция) →
Сообщество (декомпозиция PostDetail) → Активность → Профиль. Для каждого:
миграция токенов, плотность по Figma-раскадровке, FlatList где лента,
pull-to-refresh, сверка с Figma-фреймом через MCP. Чекпоинт после каждого
кластера из 2–3 экранов.

**Срез 3 — Контуры педагога, администратора, владельца** тем же методом
(TeacherToday/TeacherStudents/Assessment*, Operations, OwnerOverview,
Series, StaffLessons, CreateLesson/CreateStudent/TeacherChange/Onboarding).

**Правила каждого среза:**
- `pnpm run mobile:check` зелёный; тестов ≥ 214, число только растёт;
- новые pure-функции (расчёты лейаута, маппинги) — с юнит-тестами;
- ledger-запись с конкретными свидетельствами (какие findings закрыты);
- ничего не удалять «молча»: если поведение меняется (например, куда ведёт
  таб) — фиксируй в ledger-evidence.

---

## §7. Отчётность

Финальный отчёт сессии:
1. Таблица findings: обнаружено (P0/P1/P2) / исправлено / отложено с причиной.
2. Скриншот-чеклист для владельца: что проверить на устройстве
   (экран → ожидаемое поведение), сгруппировано по контуру ученика/педагога/
   админа/владельца.
3. Обновлённый ledger с `nextSafeAction` для следующей сессии.
4. Реестр непроверенного (обязателен и не может быть пустым): что требует
   устройства/человека (Dynamic Type на железе, VoiceOver-проход, 60fps на
   длинных лентах).

Не выдавай желаемое за сделанное: если экран мигрирован, но не сверен с Figma —
это «частично», не «готово».
